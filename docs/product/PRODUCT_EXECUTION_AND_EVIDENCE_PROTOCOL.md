# 产品基线驱动的实现、测试与真实验收协议

> 版本：1.0  
> 生效日期：2026-10-26  
> 权威产品基线：`docs/product/PRODUCT_DEEP_REVIEW_AND_TOP10_BENCHMARK.md`  
> 状态约定：`STATIC_REVIEW` / `TEST_PASS` / `RUNTIME_PASS` / `USER_OUTCOME_VALIDATED` / `NOT_RUN` / `BLOCKED` / `FAIL` / `UNKNOWN`

## 1. 目的与不可降低的验收原则

本协议将产品基线中的建议转为可追踪、可实施、可测试、可复验的工作项。产品改进不能以“代码已写完”“构建成功”或“页面可以打开”为最终验收终点。

每项改动必须在实施前、实施中和交付时持续回答：

1. **用户为什么需要它？** 指明目标用户、触发场景、现有阻碍、预期行为变化和用户价值。
2. **为什么采用这种交互？** 说明信息层级、按钮位置/优先级、默认值、操作路径、状态反馈、微文案、键盘/触控/语音行为及异常处理的设计依据。
3. **什么证据证明它更好？** 预先定义可复现的验收标准，记录实际运行结果、测试证据、对照基线及未解决风险。没有效果数据时只能说“满足验收条件”，不能声称已证明用户效果提升。

## 2. 每项工作必须有完整追踪链

每个工作项应有唯一任务 ID，并关联：

- 产品基线章节和问题/建议编号；
- 用户故事或用户任务、触发场景和现有问题证据；
- 当前实现证据、可复用能力、假设和未知项；
- 交互决策及备选方案取舍；
- 需求范围、非目标、风险、数据保护与回滚方式；
- 可测量的验收标准及测试用例；
- 代码路径、提交/PR、自动化测试结果；
- 真实运行验收记录（页面、环境、视口、数据前置条件、操作步骤、预期/实际结果、截图或日志链接）；
- 最终状态、遗留风险、任务台账和交接记录。

不得把多个独立用户问题合并成一个无法独立验收的大任务；也不得为了“完成一个 P0”而进行无边界重构。

## 3. 强制工作流

### G0：读取治理与产品上下文

1. 读取项目入口规则、AIMES Core 和任务相关 Skill 的实际正文。
2. 优先调用并执行 `.aimes/skills/product-manager/SKILL.md`；按需要路由到 `requirement-cognition`、`market-analysis`、`ui-quality-review`、`frontend-design`、`ui-implementation-validation`、架构/测试 Skill。
3. 定向读取产品基线、相关设计文档、当前实现、测试和历史缺陷。
4. 记录 Skill 文件路径和实际执行产物；只看到注册表或规则路径不算实际调用，自动路由未验证时必须标 `UNKNOWN/NOT_RUN`。

### G1：产品问题与价值定义

在写代码前回答：
- 谁在什么情况下遇到什么阻碍？
- 目前怎样完成任务，损失是什么？
- 为什么现有能力不足？是否能复用现有组件/服务/数据模型？
- 预期改善是什么，如何观察或测量？
- 解决方案有哪些，为什么推荐其中一个？
- 哪些假设需要先验证，哪些未知会阻断实现？

若产品目标存在重大歧义，先提问；低风险假设必须显式标注，不可伪装为用户事实。

### G2：交互和微文案设计

按具体页面/状态逐项设计，不能只写笼统的“优化 UI”：
- 首屏主任务与主/次操作的层级；
- 控件的位置、尺寸、相邻关系、可发现性和误触风险；
- 默认值、禁用条件、提交中、成功、空、加载、失败、部分成功和恢复状态；
- 每条关键 AI/教师提示的触发时机、目标、语气、信息量、可执行下一步和不适用场景；
- TTS/ASR/录音权限、打断/排队、静音、重试、焦点与键盘行为；
- 窄屏、缩放、长文本、触控、可访问名称、焦点可见和错误关联；
- 数据持久化、重复操作、取消、刷新、重启及恢复后的用户预期。

对每个关键交互记录“选择该设计的原因”和至少一个被拒绝方案及理由。文案不得夸大掌握效果、伪造能力或将技术失败归咎于学习者。

### G3：实现与保护

- 先检查当前主干、工作区/分支状态和既有变更；保护用户内容，不覆盖未提交工作。
- 优先最小、可回滚、可独立验证的改动；避免同时更改无关模块。
- 重要状态转换应有显式模型，不靠模糊布尔值或 UI 文案推断任务状态。
- 对生成、保存、复习计数和学习事件等有副作用操作，验证幂等性、去重、失败恢复和数据来源关系。
- 代码、测试和产品/设计文档保持一致；必要时更新任务台账与交接记录。

### G4：自动化验证

按风险选择并真实执行已有命令，不得虚构命令或结果：
- 静态检查、类型检查、生产构建；
- 纯函数/组件单元测试；
- API/存储/服务集成测试；
- 核心用户流程回归、异常/边界/重复操作测试；
- 测试数据清理与数据一致性检查。

记录完整命令、退出码、测试数量、失败详情和对应 commit。CI 只证明该 workflow 实际覆盖的检查，不自动证明浏览器交互、视觉、语音或用户效果通过。

### G5：真实运行验收

任何 UI/交互改动都必须执行适用的真实运行验证。至少覆盖：
- 目标页面和目标窗口尺寸；
- 主路径、空状态、加载状态、失败/重试和恢复路径；
- 按钮位置/层级、文本换行/溢出、焦点、键盘或触控可达性；
- 控制台与网络错误；
- 涉及 TTS/ASR 时的真实播放/录音/权限/打断行为；
- 刷新、返回、重新进入及重复点击对数据的影响。

记录环境、视口、前置数据、步骤、预期、实际、证据链接。没有真实浏览器/目标系统时，标 `BLOCKED` 或 `NOT_RUN`，并列出明确的人工补验步骤；不得将静态代码推断写成视觉或实机 PASS。

### G6：效果验证与交付门禁

- 预先定义改动前基线与可观察结果；可用时对比任务完成率、错误率、恢复成功率、操作步骤/耗时、反馈可理解度等。
- 没有真实用户样本或量化数据时，明确效果尚未被证明，只能报告技术和验收标准的满足情况。
- 所有适用检查必须 PASS，或将未完成项明确列为 BLOCKED/NOT_RUN 并说明影响；关键数据安全、重复写入、任务丢失和主要用户路径的失败不得以风险接受替代修复。
- 更新产品基线实施记录、`project-control/TASKS.md`、`project-control/HANDOFF.md`，附提交、CI 和真实运行证据。
- 只有真实证据覆盖的状态才能标记为 PASS；不得用“已实现”替代“已验收”。

## 4. 证据等级与报告措辞

| 状态 | 含义 | 允许的结论 |
|---|---|---|
| `STATIC_REVIEW` | 已阅读源码/文档，未运行 | “静态检查发现/确认……” |
| `TEST_PASS` | 指定自动化测试真实通过 | “所列测试通过”，并列命令和结果 |
| `RUNTIME_PASS` | 目标运行环境中的适用交互已真实执行并留证 | “所列场景在指定环境验收通过” |
| `USER_OUTCOME_VALIDATED` | 有方法清楚的真实用户任务或可信行为数据 | 可报告测量结果、样本/局限和前后对比 |
| `NOT_RUN` | 未执行 | 不得推断通过 |
| `BLOCKED` | 因工具/环境/权限/数据缺失而无法执行 | 说明阻断因素、影响和补验步骤 |
| `FAIL` | 已执行且不符合预期 | 记录失败证据、影响和修复/回归计划 |
| `UNKNOWN` | 证据不足或来源冲突 | 保留未知，不猜测 |

不同证据等级不得互相替代。视觉检查不能只凭 DOM/样式代码推断；学习效果不能只凭 AI 输出“看起来不错”推断；自动化测试通过不能替代目标用户任务验证。

## 5. UI 与 AI 教学微文案的专项验收

每条关键提示至少评审：
- 用户此刻的目标和所处步骤；
- 是否在正确时机出现，是否会打断思考、录音或回答；
- 是否用用户理解的词语解释操作，而不是内部术语；
- 是否只提供当前最有用的一步；
- 是否给出清晰的继续、重试、查看提示或退出选择；
- 反馈是否引用真实回答/真实学习行为；
- 表扬是否具体、诚实且有学习价值；
- 失败是否区分技术故障、识别不确定和学习者错误；
- 在不同屏幕尺寸、长文本和语音状态下是否仍然合适。

关键按钮的位置与优先级必须结合真实视口、视觉层级、键盘焦点和误触风险验证，不以“在代码里存在”作为验收。

## 6. 近期执行顺序

以 `docs/product/PRODUCT_DEEP_REVIEW_AND_TOP10_BENCHMARK.md` 的 P0 为先，不一次性重构所有模块。每轮只选择一个可独立验证的切片：
1. 教材生成：内容类型识别测试、草稿/检查点隔离、进度/部分成功/恢复；
2. 首页：主 CTA、真实数据口径、空/错误状态与恢复位置；
3. 课堂：语音打断、自动朗读、跳过/中断/完成语义；
4. AI 教学/面试：场景目标、反馈依据、重答与失败恢复。

顺序可由最新 CI、现有缺陷和真实用户阻塞情况调整，但每次调整必须记录理由。

## 7. 任务完成报告模板

每次改动交付时按以下结构报告：

1. **用户价值**：用户、场景、现有问题、预期改善。
2. **交互决策**：具体控件/位置/状态/文案、选择理由、备选方案。
3. **改动范围**：文件、数据/API 影响、提交/PR。
4. **自动化证据**：实际命令、CI 链接、通过/失败项。
5. **真实验收证据**：环境、视口、步骤、预期/实际、截图/日志链接。
6. **效果对比**：基线、结果、样本与局限；无数据时明确未证明。
7. **遗留问题**：NOT_RUN/BLOCKED/UNKNOWN、风险和补验计划。
8. **治理状态**：TASKS/HANDOFF/产品基线更新位置。

## 8. 当前协议的验证边界

本文件定义执行门禁，不证明任何特定功能已通过验收。协议本身的落地效果需通过后续任务是否实际附带上述证据来检验。AIMES 自动路由是否会在目标 IDE/CLI 自动加载并执行本协议，仍须由对应工具提供可定位的运行证据。
