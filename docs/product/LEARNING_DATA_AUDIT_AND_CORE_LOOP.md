# 学习数据审计与核心学习闭环

> 审计范围：课程、课时、练习、复习、学习计划、首页与统计；基于当前分支静态代码审查。
> 状态：代码层面已审计；尚未执行前端构建、后端测试、数据库运行验证或 Windows 实机验收。

## 1. 结论摘要

项目已有真实持久化基础，不需要再建立一套平行的学习数据系统：

- 课程、课时、课程进度、练习记录：前端仓库经 HTTP 访问本地 FastAPI 后端，SQLite 为迁移后的主数据源。
- 单词掌握度与复习日志：通过复习仓库调用后端接口，SM-2 算法在前端计算，结果持久化到后端。
- 学习计划、自定义任务、打卡快照：已有后端 API 与 SQLite 持久化；计划看板由 `GET /api/study-plans/{id}/dashboard` 聚合派生数据。
- 课堂点评：复用 `learning_records` 保存课堂模式、耗时、指标和反馈，不另建表。
- TTS Blob 缓存仍在 IndexedDB，属于可重建缓存，不应与业务学习记录混为一谈。

主要缺口不是“没有数据”，而是跨页面的消费口径、事件记录完整性和失败状态表达尚不一致。

## 2. 数据来源审计矩阵

| 业务对象 | 当前来源/持久化 | 已确认行为 | 风险与后续 |
|---|---|---|---|
| 课程/课时 | `courseRepository` → `/api/courses`、课时接口 | 通过后端 API 读取、创建、更新和删除 | 删除课程会级联清理进度和练习记录；需确保 UI 明示影响 |
| 课程进度 | `/api/course-progress/{courseId}` | 保存已完成课时、当前课时、完成比例、最后学习时间 | 过去课堂仅在完成时写入当前课时，未完成退出无法可靠恢复；本批已在进入课堂时补写当前课时，待运行验证 |
| 练习记录 | `/api/practice-records` | 练习结束后保存准确率、耗时、模式、题量和错误项 | 课时完成条件在经典练习与沉浸课堂间不完全一致，需统一完成事件语义 |
| 单词掌握度 | `/api/review/mastery` | 按单词与来源保存 SM-2 状态 | 同一个单词不同来源会形成独立记录；这是当前模型行为，后续需明确跨课程去重策略 |
| 复习日志 | `/api/review/logs` | 单次复习结果持久化，统计由后端接口提供 | 复习会话对象本身主要是内存态；持久化证据以复习日志为准 |
| 学习计划 | `/api/study-plans`、看板接口 | 计划、任务、打卡由后端保存；课时任务和进度由看板派生 | 首页原先没有消费看板；本批已接入一个进行中计划的看板摘要，待验证多个计划的优先规则 |
| 今日统计 | 练习记录、复习统计、计划看板 | 各自可以从持久化数据读取 | 三类数据并非同一指标口径；首页明确标注计划内分钟，不能冒充全局总学习时长 |
| 学习总时长 | 学习列表的 `totalStudyTime` | 学习服务以分钟累加并按 60 转小时 | 仓库类型注释原先写毫秒，与业务实现矛盾；本批已修正注释。仍需检查所有调用方的传入单位 |
| 首页继续学习 | 过去无真实恢复卡片 | 课程进度包含 `currentLessonId` | 本批新增看板服务：按最近学习课程恢复当前未完成课时；不存在可恢复课时则显示诚实空状态 |

## 3. 已确认的设计/实现问题

### 3.1 空数据与读取失败曾无法区分

`learningService.getLearningCourses()` 和 `getLearningStats()` 原先在异常时分别返回空数组和全零统计。UI 因此可能把后端故障显示成“没有课程”或“学习数据为零”。

本批已改为记录日志后重新抛出异常，让 Store/首页调用方能够展示错误状态。需要通过 API 故障注入或断开后端验证空状态与错误状态的区别。

### 3.2 学习位置没有在进入时写回

课程进度契约已经包含 `currentLessonId`，但沉浸课堂过去只在完成时同步进度。用户在未完成时退出，首页就无法可靠地知道最近打开的课时。

本批在课堂成功加载课时后，立即写入当前课时和最后学习时间，同时保留已完成课时与完成比例；写入失败只记录警告，不阻断课堂。需要验证刷新、退出重进、已完成课时、删除课时等边界。

### 3.3 学习时长单位契约不一致

`LearningListItem.totalStudyTime` 的注释原先标记为毫秒，但学习服务以分钟累加并以分钟计算总时长。本批将注释改为分钟。后续仍需检查后端 schema、历史数据和所有调用方，不能只凭注释认定历史数据单位。

### 3.4 完成课时的业务语义不一致

- 经典练习：准确率达到 80% 才调用完成课时。
- 沉浸课堂：完成点评流程时同步课时完成状态，精读/词根的完成行为不等同于同一套答题准确率。
- 进入课堂：本批开始持久化当前课时，但不会将其标为已完成。

建议统一事件语义：`lesson_started`、`practice_submitted`、`lesson_completed`、`lesson_abandoned`。课程完成状态应由明确的完成事件产生，而不是简单把“打开过”“练习过”混为一谈。

### 3.5 统计不能把不同来源的分钟直接相加

练习记录耗时、课堂点评耗时、学习列表累计分钟、计划看板分钟可能覆盖不同活动或存在重复记录。当前首页分别显示“今日练习次数”“今日复习词数”“计划内学习分钟”，不将它们合成一个未经核实的总学习时长。下一步应基于统一学习事件定义唯一统计口径，并为旧数据制定迁移/兼容策略。

## 4. 本批实现

- 新增 `frontend/src/shared/services/learningDashboardService.ts`，聚合学习课程、课程进度、到期复习、复习统计、今日练习记录和进行中计划看板。
- 首页新增继续学习、今日学习、计划任务、复习建议和学习总结入口。
- 继续学习目标从持久化的 `currentLessonId` 读取；若该课时已完成或失效，则选择课程内第一个未完成课时。
- 没有可恢复课时时显示空状态，不生成虚构的学习数据。
- 读取失败以警告提示呈现，允许部分数据降级。
- 课堂进入时保存当前学习位置。
- 学习列表读取失败不再伪装成空列表或零统计。
- 修正累计学习时长字段注释为分钟。

## 5. 核心学习闭环的验收标准

- [ ] 首页继续学习能进入上次未完成课时，而不是仅返回课程详情。
- [ ] 刷新/关闭后重开，当前课时仍可恢复。
- [ ] 课程删除、课时删除或进度记录指向不存在课时，不会导致首页空白或路由错误。
- [ ] 没有课程、没有待复习词、没有计划是可理解的空状态。
- [ ] 后端离线或接口失败时显示错误/降级状态，不伪装成全零数据。
- [ ] 首页、我的学习、课程详情、统计页的课程进度一致。
- [ ] 练习完成、课堂完成、退出恢复的事件语义有明确区分。
- [ ] 学习时长单位和去重规则经后端 schema、历史数据及调用点核对。
- [ ] 计划任务的勾选、跳过、删除和打卡在重启后保持一致。
- [ ] 复习结果保存后，到期数量和今日复习数随之更新。

## 6. 下一阶段：统一学习事件契约

建议事件最小字段：

```ts
interface LearningEvent {
  eventId: string
  eventType:
    | 'lesson_started'
    | 'lesson_completed'
    | 'lesson_abandoned'
    | 'practice_submitted'
    | 'review_submitted'
    | 'study_plan_task_completed'
  courseId?: string
  lessonId?: string
  activityId?: string
  occurredAt: number
  durationMs?: number
  result?: {
    correctCount?: number
    totalCount?: number
    accuracy?: number
  }
  metadata?: Record<string, unknown>
}
```

该契约是后续设计建议，不代表本批已创建事件表。实施前需确定事件幂等键、旧数据兼容、学习时长去重、课程/课时删除后的历史保留策略，再决定是扩展现有表还是新增统一事件表。
